# User-environment Feeding Frenzy JSON-WS wrappers

This folder holds the tool graph that new authenticated embedded Feeding Frenzy chats load when they run in a Buffaly User environment. Existing conversations and all Root sessions keep the wrappers in the parent folder.

## Ownership

- **Generator:** `scripts/generate_feeding_frenzy_user_wrappers.ps1`. Run it after changing any parent wrapper listed below. Run it with `-Check` to fail when the committed copies are stale; `FeedingFrenzyUserEnvironmentTests.GeneratedUserWrappers_AreCurrentAndRecorded` runs that check.
- **Do not hand-edit generated files.** Each starts with `// GENERATED by Scripts/generate_feeding_frenzy_user_wrappers.ps1`.
- **Hand-written files** (edit directly, with history below): `Foundation.pts`, `SalesRepresentative.pts`, `Administrator.pts`, `UserDocumentSigning.Admin.pts`.

## Why a separate copy exists

User source may call only `[UserEnvironmentFacade]` statics (Buffaly.Agent.Host `UserSharedGraph`). The Root wrappers build arguments with `BasicUtilities.JsonObject`, which User source cannot import. The generator rewrites only that argument building to `FeedingFrenzyUserJsonWs` string builders (`NewArgs`, `SetString`, `SetInt`, `SetBool`, `SetDouble`, `SetNull`, `SetObject`, `LeadRowFromResponse`, `IntText`, `BoolText`, `IsEmpty`). Action names, parentage, `Execute` signatures, routes, argument names and JSON value types are preserved. Any line the generator does not recognise fails generation instead of being copied or guessed.

## Not available to User sessions

These Root capabilities stay Root-only. The parity test excludes exactly these names and fails if any appears in a User graph.

- `ToCreateFeedingFrenzySigningDraftFromUploadedMarkdownFile` (AgreementTemplates.Admin), `ToCreateFeedingFrenzyUserSigningDraftFromUploadedMarkdownFile` and `ToCreateFeedingFrenzyUserSigningDraftFromLocalMarkdownFile` (UserDocumentSigning.Admin): they read a path on the Buffaly worker (`File.Exists`, `File.ReadAllBytes`, `Path.GetExtension`). User source has no file access, and a facade that read worker paths for a User session would widen native access. The inline-Markdown actions (`ToCreateFeedingFrenzySigningDraftFromMarkdown`, `ToCreateFeedingFrenzyUserSigningDraftFromMarkdown`) are available.
- `ToResearchFeedingFrenzyAutomationProspect` (Automations.Admin): native web research through `_opsAgent`. The User runtime gets no `_opsAgent`, no Buffaly User facade offers model or web research, and an FF facade cannot reach the host agent runtime. Closing this needs a core Buffaly User research facade.
- `ToWriteFeedingFrenzyAutomationDraftsSkill` (Automations.Admin): a PromptAction whose workflow requires that research step, and whose prompt lives outside the shared `Prompts/` roots a User graph may read. Moving the prompt alone would publish a workflow whose required step is unavailable.
- `Skills/FeedingFrenzySms/Reply.pts` (`FeedingFrenzySms_SendCurrentReply`): uses `_opsAgent` and the Root SMS facade. Neither User entry includes it.
- The explicit tenant bindings (`FeedingFrenzyJsonWsService#Medek`, `#Affinity`, `#Local`) are Root diagnostics only.

## History

### 2026-11-19 - Initial User-environment graph

- **What:** Added the generator, the 25 generated wrappers above, and hand-written `Foundation.pts` (User `FeedingFrenzyJsonWsService` and `#Current` backed by the `FeedingFrenzyUserJsonWs` facade), `SalesRepresentative.pts` and `Administrator.pts` (role graphs mirroring `../SalesRepresentative.pts` and `../Administrator.pts`).
- **Why:** New authenticated embedded chats must run in a genuine Buffaly User environment while keeping the role-specific CRM tools. Root wrappers cannot compile under User import rules.
- **Session binding:** `Foundation.pts` keeps the Root service and `#Current` names, so the embedded launch's `RunProtoScriptMethod(FeedingFrenzyJsonWsService#Current.ConfigureAuthorization)` binds unchanged. The facade pins the first launch URL for the per-session worker; a later bind to another installation is rejected, and a token refresh for the same installation is allowed.
- **Validation:** `generate_feeding_frenzy_user_wrappers.ps1 -Check` and `FeedingFrenzyUserEnvironmentTests` (role action and signature parity, forbidden-token scan, facade binding tests): 92/92 passed on 2026-11-19 (Release, explicit Host SDK). Compilation by the Host User composer is proven only by the staging launch.

### 2026-11-19 - Agreement templates and user document signing for User sessions

- **What:** Generated `AgreementTemplates.Admin.pts` (11 of 12 actions) and hand-wrote `UserDocumentSigning.Admin.pts` (5 of 7 actions); `Administrator.pts` includes both in the Root order. `Foundation.pts` adds `ConfigureAutomationUser(Email)`.
- **Why:** These administrator tools were previously excluded without an accepted contract conflict. Only the local-file variants have one (see above).
- **Actor:** Root wrappers send `#Current.AutomationUserEmail` as the signing actor assertion. In User sessions the embedded launch binds the authenticated user's email through `ConfigureAutomationUser` after `ConfigureAuthorization`, and the generator rewrites the property to `FeedingFrenzyUserJsonWs.AutomationUserEmail()`. The server still derives the actor from the token principal and requires an Administrator with a matching email, so the binding grants nothing.
- **Signing transport:** Root calls `FeedingFrenzy.UserSigning.Client.SigningClient`, which User source cannot import. The facade sends the same `user-document-signing-requests/*-as-automation` routes, argument names and validation order to the pinned installation.
- **Validation:** recorded in the companion history of `FeedingFrenzyUserEnvironmentTests.cs`.

### 2026-11-19 - Thin pass-through wrappers (code review P2 on eccb6eb)
