# Action Learning Coordinator ProtoScript

Defines `SessionWorkCoordinatorSkill` as the common coordinator base, with `ActionLearningCoordinatorSkill` and `OntologyFoundryCoordinatorSkill` as specializations.

The reusable workspace contract adds `SessionWorkWorkspaceDefinitionProvider`, `SessionWorkPortfolioProvider`, and `SessionWorkItemWorkspaceProvider`. The dashboard binds to one specialization, calls `ToGetSessionWorkCoordinatorInfo(specialization)`, and then invokes only the provider names advertised by that live coordinator. Action Learning and Ontology Foundry use one renderer.

`ActionLearningCoordinatorEntityRoot` is the restricted semantic entity root required by the `action-learning-coordinator` agent profile during fresh-session initialization.

The first staging slice exposes common live-runtime methods for coordinator identity, reading and initializing the fixed ledger, typed add/remove of exact source-session entries, and a bounded attachment-choice inventory. Add is idempotent; removing an absent entry returns `NotFound` without changing state. The raw whole-ledger replacement surface is intentionally not public.

All common methods derive from `SessionWorkCoordinatorSkillAction`; specialization methods use `ActionLearningCoordinatorSkillAction` or `OntologyFoundryCoordinatorSkillAction` as their primary action base while retaining the shared provider contract as a secondary base. Coordinator agent profiles root tool discovery at the concrete `*SkillAction` prototype so bounded autonomous operations are callable without exposing sibling specializations. State is stored at `artifacts/session-work/ledger.json` in the coordinator session. The WebModule calls these methods through `BuffalyAgentService.RunProtoScriptMethodAsync`; it contains no coordinator business logic.

The first specialized operation, `ToAttachActionLearningWorker`, creates or reuses an `action-learning` worker with the exact source session as its parent and records the worker binding in the ledger. Both specialization attachment actions validate the exact source, worker profile, worker parent, deterministic-worker conflict, and same-ledger ownership before creating or recording anything. A blank worker choice creates or reuses `<source><specialization suffix>`; an advanced non-deterministic worker key must already exist and satisfy every identity check. `ToListActionLearningCoordinatorActions` provides the exact common, specialized, and worker action inventory rendered by the two-level dashboard; the worker inventory includes `ToRefreshActionLearningSessionCandidatesSkill` as the primary living-artifact stage.

`ToGetActionLearningSourceWorkspace` delegates its fixed source artifact to `ActionLearningCandidateProjection`. The facade recognizes the historical `## Ranked candidates` report and the current v2 `Last Accepted` or `Proposal Under Review` candidate sections, returning typed action-candidate rows. This allows existing evidence-rich reports to remain visible without rewriting them merely for display, while current incremental reports use the same dashboard contract.

The package also carries the canonical Ontology Foundry worker profile, master prompt, and complete `Skills/OntologyFoundry` prompt-skill tree so `ToAttachOntologyFoundryWorker` can create the real restricted worker in every installation. The Foundry source provider delegates parsing of the stable eight-column `## Ranked entity resolutions` table to the packaged `OntologyFoundryProposalProjection` facade, keeping ProtoScript as thin orchestration glue. It returns the complete source-owned EvidenceGraph, a bounded raw `ProposalMarkdown` fallback, and a typed `ProposalProjection` containing source identity, derived Existing/NewCandidate/Ambiguous/Rejected counts, and ranked rows with entity, importance, resolution, prototype candidates, search evidence, detail evidence, and reason. It also returns typed `WorkerActions` descriptors for refresh/index evidence, Expand-and-Enhance, physical-peer Generalize, and ProposeBuild; descriptors carry exact prototype, label, description, category, mode, and availability. Table rows are authoritative; malformed row shape or unknown resolution fails explicitly. The shared browser renders the typed proposals and action descriptors and links the complete artifact; it does not parse domain Markdown.

The Online Memory Critic Batch specialization uses the actual deterministic `<source>-online-memory-critic` child as the worker instead of creating a separate runner. `ToReconcileOnlineMemoryCriticBatchLedger` discovers existing exact-profile children and records their source bindings idempotently without changing enabled state, subscriptions, provider/model/reasoning settings, manifests, or queued work. `ToAttachOnlineMemoryCriticBatchWorker` validates an explicitly selected child and preserves the same operational settings. `ToRunOnlineMemoryCriticBatchOperation` supports reset, run-next, run-all, and additive Catch up through the same generic worker-action contract. Catch up computes exact missing source turns from correlated critic result markers and active manifest work, appends only those gaps oldest-to-newest, and reuses the existing concurrency-one continuation. Host/web callers must create a missing critic child before invoking coordinator attach; the coordinator worker intentionally does not create foreign runtimes.

The Online Action Critic Batch specialization exposes the same shared workspace contract for genuine historical replay through `<source>-online-action-critic`. Its reset operation rebuilds the manifest from complete source history oldest-to-newest; run-next and run-all dispatch through `OnlineActionCriticBatchProjection` and preserve existing `SessionActions.pts`, action revisions, turn reviews, and suspected bugs.

The Action Learning workspace now advertises `ToRunActionLearningWorkerOperation`. It resolves the exact ledger-bound worker and delegates guarded reset, start-from-beginning, discovery, metrics, grounding, and evaluation operations to the typed C# projection. Reset/start preserve the deterministic worker attachment and use the dashboard's normal confirmation dialog before generated source-owned Action Learning state is cleared; they do not require a typed confirmation phrase.

Action Learning attachment follows the foreign-runtime boundary: the browser/host creates a missing deterministic worker with the source as parent, then worker-owned `ToAttachActionLearningWorker` validates the existing worker's exact key, profile, and parent before recording it in the coordinator ledger. The coordinator worker never calls `CreateAgentFromProject` for a foreign worker session.

`ToAttachOntologyFoundryWorker` applies the same source-child pattern with the `ontology-foundry` profile. `ToRunOntologyFoundryWorkerOperation` is the single bounded dispatcher advertised by the Foundry workspace definition. Its thin ProtoScript wrapper resolves only the attached worker key from the coordinator ledger and passes four strings to the packaged C# facade. The facade verifies the exact source and worker inventory rows, enforces the source-parent and `ontology-foundry` profile boundary, freezes the source's canonical inventory snapshot, accepts only the four provider-advertised action prototypes, validates the required seed or promoted-candidate input, and dispatches an exact assignment through the typed worker service. Keeping native `SessionInfo` and `EvaluateResponse` values inside the facade avoids lossy ProtoScript local conversion. Refresh, Expand-and-Enhance, Generalize, and ProposeBuild remain governed by their prompt-level read/write guards; the dispatcher does not add ontology authoring, Session Entity Index materialization, or arbitrary prototype execution.

The browser does not read session files or parse domain Markdown. Each source-workspace provider validates the exact source key and reads only its fixed source-owned artifact. The logical browser route and static assets use `/web-modules/SessionWorkCoordinator`; the legacy `/web-modules/ActionLearningCoordinator/dashboard` route redirects with its query string preserved while the physical package ID remains unchanged. A packaged workspace registry binds each page specialization to its exact coordinator session and agent profile, and the live workspace-definition identity must match before rendering. New ledgers identify `SessionWorkCoordinatorSkill`; existing version-1 Action Learning ledgers remain readable and are not rewritten merely by loading the workspace.
